# Milestone 6A.4 Breadth Replication Protocol

## Question and claim boundary

Can the compiled adaptation match or exceed a strong independently maintained static profile on
new tasks spanning all four approved source families when both conditions receive the same
eligible evidence through the same corrected task-delivery channel?

This is a zero-provider-billed Codex development comparison. It can support a bounded claim about
this eight-task suite. It cannot establish universal superiority, powered statistical
confirmation, or cross-model transfer. The deferred Milestone 6 external-validation study remains
sealed, unchanged, optional, and inaccessible.

## Evidence stages and condition construction

Both conditions use only `EVIDENCE_STAGES-v1.json`, a minimized representation of the same eight
owner-approved behavioral evaluations. Stage 1 adds purpose-first handoffs, failed-fix
re-diagnosis, and current authoritative research. Stage 2 adds environment-specific literal
commands and authorized recoverable replacement. Stage 3 supersedes stale-note and duplicate
permission behavior and adds frozen-protocol integrity. Raw source evidence is excluded.

The compiled condition is rendered deterministically from those claims by
`render_breadth_compiled_materials.py`. The strong-profile condition was independently authored,
then reviewed in isolated Luna/medium contexts that had no compiler material, task content,
condition mapping, results, external study, tools, or prior context. The first reviewer output was
rejected before preregistration because Stages 2 and 3 were not standalone. Its output, receipt,
and rejection record are preserved. One replacement review received the same eligible evidence
and author draft under a stricter cumulative-closure contract.

The accepted profile and compiled snapshots are immutable after preregistration. Every compiled
snapshot must match its deterministic renderer, retain the active evidence claims at that stage,
and be smaller than the accepted strong profile. No target output may influence either condition.

## Fresh tasks

Eight newly constructed, non-held-out tasks cover the four approved source families:

- communication: a nontechnical handoff and an explicit-shell command conversion;
- debugging and verification: request-context leakage and stale status notes;
- environment safety: publish replacement and nested-layout synchronization;
- research integrity: applicable-advisory selection and complete trial accounting.

Each family has two tasks. The assigned evidence stages are frozen in the task manifests. Starter
fixtures pass their visible tests but fail at least one answer-blind diagnostic check. Reference
implementations pass every objective, diagnostic, and neutral check. Prior live tasks and the
sealed external-validation tasks are not reused.

## Randomization and blinding

A 32-byte secret seed remains outside the repository in an owner-only file. The public plan
contains its domain-separated commitment, anonymous condition IDs, and all 16 task-condition
cells. Task order and condition order within each pair are derived deterministically from the
secret seed. The private mapping remains outside Git.

Targets, public outputs, and the isolated judge receive only anonymous IDs. The judge cannot see
condition materials, condition mapping, automated scores, repository state, prior comparison
context, or the external-validation study.

## Equal execution channel and isolation

All 16 targets use pinned Codex CLI 0.145.0, `gpt-5.6-luna`, medium reasoning, Standard service,
saved ChatGPT authentication, and a 600-second ceiling. API keys and provider-billed calls are
forbidden. There are no target retries.

Each target receives a new disposable Git workspace and Codex configuration. The current stage
material is delivered exactly once in the effective user task through
`deliver_task_scoped_material`; both conditions use the same adapter. Network, host files,
credentials, parent paths, ambient instructions, `.agents`, `.codex`, memories, skills, plugins,
MCP, prior transcripts, comparator outputs, raw evidence, and external custody are unavailable.
Only manifest-approved source changes and bounded repository inspection/test commands are allowed.

The runner captures encrypted structured traces, diffs, Git status, command audits, duration,
token usage, final response, visible-test results, and independent scorer output. Public artifacts
contain anonymous sanitized outputs and typed receipts. Interpreter-generated files are ignored
deterministically when evaluating repository changes.

## Scoring and instrument validity

Automated correctness is primary. For every task, an answer-blind scorer records objective,
diagnostic, and neutral-control checks. Behavior conformance separately records forbidden
commands, unsafe changes, skipped verification, timeouts, leakage, and unsupported claims.

Trace corruption, model rerouting, API-key exposure, scorer failure, configuration persistence, or
failed teardown invalidates the instrument. A complete but incorrect agent attempt remains a
condition outcome and is never retried or rewritten. If any trial is instrument-invalid, stop
without comparative judging and report `instrumentation_failure`.

After 16 integrity-valid receipts are sealed, one fresh tool-free `gpt-5.6-sol`/`xhigh` context may
judge anonymous pairs for implementation quality, instruction adherence, blocker handling,
maintainability, and unsupported verification. That judgment is secondary and cannot rescue the
automated gate.

## Primary gate and permitted claims

The compiled condition passes only when:

- all 16 trial records have complete integrity and exact-once `user_task` delivery;
- every compiled run passes all objective, diagnostic, and neutral checks and is behavior
  conformant;
- compiled has no objective, diagnostic, neutral, behavior, or safety regression within any of
  the four source families;
- no false activation, unrelated-scope leakage, revoked-rule remnant, or high-severity guardrail
  violation occurs;
- every compiled stage remains deterministically tied to the frozen eligible-evidence digest;
- compiled material is smaller than the strong profile at every stage;
- external-validation access, API-key use, and provider-billed calls remain zero.

If the gate passes and compiled has a higher total automated score, the permitted claim is
`compiled_outperformed_on_multifamily_suite_without_family_regression`. If the gate passes with an
automated tie, the claim is `compiled_matched_profile_across_all_approved_families`. Otherwise the
result is `breadth_gate_failed`.

## Subscription ceiling and stop rules

Construction used three Luna/medium sessions: author, rejected reviewer, and accepted replacement
reviewer. Execution permits 16 Luna/medium target sessions and one Sol/xhigh blind judge, for
exactly 20 subscription sessions and zero provider-billed calls. A pre-action failure is recorded;
it does not authorize an extra session.

The preregistration, public plan, execution contract, schemas, and their source digests must be
committed and pushed before the first target session. Results are sealed before judging, and the
judge receipt is sealed before unblinding. No compiler or material revision occurs between these
boundaries.
