# Temper over SkillKit

October 15, 2026 owner direction: reuse SkillKit, remove duplicated manager work,
and make Temper choose and maintain an appropriate setup for each repository and
work goal. Personalization is part of that product, not an optional feature to
leave out of the usefulness comparison. No GitHub CI.

The product promise is: **Keep my agent setup appropriate for this work, and learn
how I like to collaborate, without making me maintain either by hand.**

## Responsibilities

SkillKit supplies skill discovery, its recommendation engine, native installation,
updates, translation and persistent manager configuration wherever those existing
interfaces meet the required contract. Its documented session memory is existing
functionality, not a unique Temper feature.

Temper owns the scoped decision about what this task needs, keeping irrelevant
capabilities inactive, adapting to changed project context, and recovering without
overwriting the owner's work. Its governed habit learner is responsible for
personal defaults, contradictions, applicability and undo. Repository requirements
are context for selection, not evidence of personal preferences. Selection by an
agent is not an independent human observation. No second selector model is needed
when the connected work agent can make the decision.

Do not add another marketplace, general installer, translation layer, or memory
store solely to duplicate a manager's existing capability. Retain additional
ownership/integrity/recovery controls only where their needed behavior is
demonstrated. Support for an arbitrary framework is not established by installing
some of its SKILL.md files.

## Current local change

New persistent hubs default to SkillKit. Their admission checks require SkillKit
and Node, without requiring the separate Skills CLI. Explicitly configured legacy
Skills-backed hubs keep their saved manager and checks. No existing hub is silently
converted. Installation still goes through the selected native manager. Full
resource checks, manual-edit protection, scoped decision caching and recovery stay
intact. This is an initial dependency cleanup, not a completed manager consolidation
or proof that the earlier wall-time gap has disappeared.

The frozen nine-session study remains unchanged. The later source is a new
candidate and cannot be admitted by rewriting the old protocol's bindings.

Local verification: 29 focused hub/timer/grader tests passed, with Ruff and Mypy
passing. Five fresh-process native lifecycle fixture journeys passed (70 CLI
processes total), exercising switches, controlled updates, known-good recovery,
manual-edit protection and safe removal. A separate native run initialized,
registered and installed through SkillKit with the Skills CLI absent from PATH.
These checks used no model turns. They establish mechanics, not a real-work speed
or owner-effort improvement. No app was replaced, no source was synchronized to
the Mac, and no GitHub CI or release action was performed.

## Personalization activation

The owner has requested activation. A live supported enable operation on October
15 was refused before mutation: the native runtime has no installed calibration
release and its factory does not connect a calibration verifier. The existing
grant covers only the portfolio project; no inferred habits are currently stored.
Learning is enabled, while personalization and automatic serving are disabled.
This is an implementation/evidence blocker, not missing user authorization to try
the supported control. A queued request, flipped boolean or fabricated calibration
record must not be reported as working personalization.

The owner chose to proceed with calibration and improve the learner as results
identify problems, instead of implementing an unvalidated private-serving mode.
Keep the calibrated release requirement. The current source adds a read-only
calibration-evidence verifier; the installed package has not been replaced and
no personal calibration, grant, profile or serving state was changed. Expanding
observed projects or destinations remains a separate scoped permission decision.
See [the calibration continuation](TEMPER_CALIBRATION_OCTOBER_15.md).

## Test the useful difference

Compare a native agent using SkillKit with a native agent using Temper over the
same SkillKit version. Allow both to retain state and automate maintenance. Start
with a repository and a real work goal, without telling either side which skill
to choose. Include a project switch, compatible update, broken update and recovery.

Record owner research, configuration, decisions, review, maintenance and measurement
effort as well as waiting, agent time, errors and storage. Agent runtime is not
owner effort. Keep setup costs and failures, including the new layer's overhead.
Measure inappropriate activation and task regressions as well as corrections and
successful recovery. Include actual personalization only once it is running;
label controller-only studies as such.

The existing owner-effort trial has no recorded participant intervals yet.
Its effort benefit remains unknown. Do not invent owner work or replace missing
attention data with generated agent sessions. A feature count or a successful
recovery that both systems achieve does not establish a benefit for Temper.

If the additional layer does not save attention at acceptable correctness and
maintenance cost, simplify it further instead of expanding the feature catalog.
