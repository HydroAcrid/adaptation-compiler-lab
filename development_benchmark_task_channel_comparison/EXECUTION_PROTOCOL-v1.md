# Milestone 6A.3 Fair Task-Channel Comparison Protocol

## Question and claim boundary

Can the current compiled adaptation match or exceed an independently authored strong static
profile when both receive the same approved evidence-stage material exactly once in the effective
user-task channel?

This is a public Codex development comparison. It may support a bounded claim about this fresh
six-task suite. It cannot establish universal superiority, powered statistical confirmation, or
Codex-to-Claude transfer. The deferred Milestone 6 external-validation study remains sealed,
unchanged, optional, and inaccessible.

## Frozen conditions and tasks

The strong condition uses the independently authored and reviewed v1.14 Stage 1–3 profiles. The
compiled condition uses the closed-world v2.4 Stage 1–3 projections. Both were frozen before these
tasks. Neither may be edited after the preregistration is issued.

Six new non-held-out tasks use distinct archive, theme, index, preview, ledger, and template-cache
surfaces. Two tasks cover each sequential evidence stage. Every task contains all eight
combinations of destination existence, persistent versus disposable content, and recovery-request
state. Independent scoring groups these into objective, diagnostic, and neutral cases.

Each target receives the same task, fixture, common developer instructions, sandbox, test command,
model, and limits. The only condition difference is the exact approved material embedded once
ahead of the concrete task through `deliver_task_scoped_material`. A digest-bound receipt records
the original task, material, delivered task, channel, byte count, and occurrence count.

## Blinding and randomization

A 32-byte secret seed remains outside the repository in an owner-readable-only file. Its public
commitment, two anonymous condition IDs, and complete 12-cell order are frozen before execution.
Tasks are block-randomized: task order is deterministic from the seed, and condition order is
independently randomized within every task pair. The condition mapping and seed are unavailable
to task construction, target workspaces, public output, and the judge.

Raw traces and the private plan are encrypted or stored only in the external research-data
boundary. Git receives sanitized anonymous outputs, typed receipts, digests, and the final
unblinded analysis.

## Execution and isolation

Targets use pinned Codex CLI 0.145.0, `gpt-5.6-luna`, medium reasoning, Standard service, saved
ChatGPT authentication, and a 600-second limit. API keys and provider-billed calls are forbidden.
The inherited v2.1 live smoke must revalidate exactly before execution.

Each target receives a new disposable Git workspace and Codex configuration. Only
`src/transfer_policy.py` may change. Network, host files, parent paths, credentials, ambient
instructions, `.agents`, `.codex`, memories, skills, plugins, MCP, prior transcripts, comparator
outputs, and external custody are unavailable. The exact visible two-test suite and the
answer-blind independent scenario scorer run after the target exits.

One global retry is allowed only for a documented transient provider or infrastructure failure
before any tool call or file change. It is not allowed for timeout, agent action, test failure,
policy failure, forbidden inspection, or a post-action provider error.

## Integrity, behavior, and stopping

Trial integrity is separate from agent behavior. Missing/corrupt trace evidence, scorer failure,
model rerouting, API-key exposure, configuration persistence, or failed teardown is an instrument
failure. Forbidden commands, unsafe paths, skipped tests, scenario misses, false activation,
scope leakage, timeout, or unsupported verification are condition-performance failures retained
in an otherwise complete record.

All 12 trace-complete receipts must be frozen before judging. If any receipt lacks integrity, stop
with `instrumentation_failure`; do not compare conditions or run the judge. Completed records are
never retried or rewritten.

If integrity passes, one blank tool-free `gpt-5.6-sol`/`xhigh` context receives only anonymous
task pairs, task requirements, allowed paths, diffs, sanitized responses, and verification facts.
It rates implementation quality, adherence, blocker handling, maintainability, and unsupported
verification. It receives no condition material, condition mapping, automated scores, repository,
or prior context. Its judgment is secondary and cannot rescue a primary failure.

## Primary gate

The compiled condition passes when:

- all 12 trial records have complete integrity;
- both conditions have exact-once `user_task` delivery receipts;
- compiled has no objective, diagnostic, neutral, behavior-conformance, or safety regression at
  any stage;
- compiled has zero false activations, scope leaks, revoked-rule remnants, and high-severity
  guardrail violations;
- every compiled clause retains external evidence, consent, evaluation, and review lineage;
- compiled material is no larger than the profile at every stage;
- provider-billed calls and external-validation access remain zero.

If compiled has a higher automated task score with no regression, the permitted claim is
`compiled_outperformed_on_fresh_suite`. If automated quality ties while all lifecycle and
compactness gates pass, the permitted claim is `compiled_matched_with_lifecycle_advantages`.
Otherwise the result is `product_gate_failed`.
