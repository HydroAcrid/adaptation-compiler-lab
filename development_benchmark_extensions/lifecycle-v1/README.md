# Extension setup, compatibility and recovery screen

This follows the real-repository repair comparison, which found no added quality
benefit from selecting guide paragraphs. The question here is whether project
setup and recovery offer a useful infrastructure opportunity. No GitHub CI is
used. The prior comparisons and habit-learning release evaluations stay unchanged.

## Three distinct evidence layers

1. **Broader native probes:** five fresh disposable project profiles for each of
   nine routes covering pstack (full, selective and temporary), Ponytail,
   Superpowers, OpenSpec, Spec Kit, GSD Core and Pi/Ponytail registration. These
   execute real pinned native tools. GSD role/hook creation and Pi registration
   do not prove client acceptance, agent behavior or authenticated model use.
2. **Current Temper admission:** actual Foundry inspection of those source forms,
   including quarantined executable resources and unsupported non-skill inputs.
   Intake is not installation. A profile that loses required runtime capabilities
   is not counted as an equivalent setup or a performance benefit.
3. **Operator comparison:** eight fresh native Codex turns, two real historical
   codebases, two conditions and two repetitions, with identical requested source
   skills, model, effort, tools and 300-second/60-tool budgets. The comparator is
   competent selective native use, including normal backups or authored helpers.
   The other condition gets a small benchmark-only Temper publishing prototype.
   No automatic semantic router or released general installer is being tested.

## Workflows and functional acceptance

Use full starting Temper/Python and Kairn/TypeScript repositories from the pinned
real-repo study. Configure the requested pstack/Ponytail/Superpowers skills with
their complete source resources. Verify setup, then inject a partial-copy fault:
one SKILL.md is corrupted, a supporting reference is removed, and a temporary
marker appears. Concurrent owner notes and a project-policy edit must survive.
Recover, verify the complete source again, then uninstall while preserving owner
material, unrelated settings, app code and registry consistency.

The source choices are explicit so this measures lifecycle management, not whether
the model or product can automatically choose the ideal framework. The two
conditions must produce identical required file bytes at setup/recovery. Extra
unrequested installed skills fail the scope check. Supporting scripts are retained
in this experiment rather than claiming savings by discarding functionality.

Host-controlled `lifecycle_checkpoint` and `lifecycle_fault` commands enforce the
sequence. They reveal missing paths and injected damage, not reference solutions.
The fault is deterministic file corruption/dropout, not a claim that a process
was killed. A separate subprocess control actually kills the publishing prototype
after two file replacements and checks safe restoration and owner-edit handling.

## Prototype boundary

`scripts/extension_lifecycle_manager.py` operates only on marked disposable test
projects. It does not run upstream installers. The operator uses the same native
installer in a staging project, then previews and publishes exact files into the
real project. It journals undo, rejects stale previews and unapproved overwrites,
binds authorized replacements to current digests, and preserves external edits
on removal. It overlays files rather than deleting unknown files in a skill dir.

This is new experimental code. It is not part of the installed Temper app, a
signed product integration, automatic compatibility/routing logic or a change to
the Foundry's executable quarantine. Its extra setup, instructions, staging,
journals, recovery and development effort must all remain visible.

## Measurement and interpretation

Check correctness before interpreting cost. Record successful complete workflows,
owner-file loss, unresolved conflicts, scope mistakes, actual tool calls, nonzero
exits, cached/uncached input, output and reasoning. Reasoning is a subset of output.
Capture whole-trial wall time from extraction through native auth/catalog setup,
operator execution, checkpoint/fault work, fixed verification, encrypted evidence
persistence and safe cleanup. Tool/component timers are nested and not added twice.

Track observed writable scratch footprint after each tool call, including backups,
staging and journal files. This is a lower bound on transient peaks. Observation
time is recorded separately, and whole timings are instrumented rather than
ordinary production runtimes. Source acquisition, runtime provisioning, controls,
failed admission attempts and prototype development are separate shared overhead.
Human discovery, active coordinator time and coordinator tokens are unavailable,
never zero. This study cannot establish proven net ownership-cost savings.

The model is the configured catalog-verified `gpt-6.1-sol`, `medium`, using saved
ChatGPT auth, no API keys or model fallback. Capacity must be known and at least
20% before each native turn. All executable tooling is read-only in each
credential-free WSL namespace. Trials use private HOME/config trees and no network.
Native Codex skill discovery is separately checked through the real `skills/list`
interface; metadata discovery is not proof of loading or following a skill.

Model trials alternate order by repository/repetition. All outcomes are retained;
there is no tuning or selective rerun after observing trial results. Two repeats
are a development screen, not a general speed/efficiency claim. Mechanical probes
use five fresh profiles but have preinstalled dependencies and warm source caches.
Concurrent read-only admission activity and uncontrolled host load are disclosed.

Raw responses and native events remain encrypted outside Git and Obsidian. Shared
results contain only sanitized counts, timings, hashes and check outcomes. No
personal grants, learning state, adaptations, native instructions or installed
Windows/Mac applications are changed. Runtime probes do not invoke another
provider's model or copy credentials into Pi/GSD.

## Reproduction

This Windows/WSL development instrument uses local runtime paths declared in
`scripts/extension_lifecycle_sandbox.py`. Source commit/archive bindings are in
`sources.json`; npm distributions have separate registry integrity/gitHead records
because a repository HEAD is not necessarily the published package commit.

Run non-model controls and probes into new private output directories:

```text
.venv\Scripts\python.exe -m scripts.probe_extension_lifecycle controls --output <new-private-controls>
.venv\Scripts\python.exe -m scripts.probe_extension_lifecycle native --output <new-private-native-probes>
.venv\Scripts\python.exe -m scripts.probe_extension_lifecycle foundry --output <new-private-foundry-probes>
```

After the exact source/input freeze and local commit:

```text
.venv\Scripts\python.exe -m scripts.run_extension_lifecycle_screen --output <new-private-run>
```

No mode promotion, package release, GitHub push or market claim is implied.
