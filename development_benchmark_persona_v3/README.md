# Persona Effectiveness v3 — Frozen Construction Smoke

This directory freezes the successor persona-evaluation design before any new agent session. The
only authorized execution in this iteration is one construction smoke for the fresh fictional
persona `sable`. It calibrates the measurement instrument; it does not count as evidence that
Temper is effective and it does not authorize the 24-case v3 grid.

## Why this smoke exists

The failed v2.1 comparison mixed a model scope-classification problem with the question Temper was
meant to answer. V3 gives both construction lanes the same trusted host-owned scope registry and
uses deterministic policy for artifact routing. AI roles may interpret language and author a
profile, but they cannot create authoritative scope or route values.

The smoke checks that both lanes can recover the same two active behaviors from the same seven
visible turns:

- one durable project preference; and
- one durable production-incident procedure that is narrower than the normal preference.

Ordinary requests and task-only constraints must not become active learning.

## Authorized roles

Exactly three fresh, tool-free Codex sessions are allowed:

1. one `gpt-5.6-luna` semantic-sensor session at medium reasoning for the compiled lane;
2. one `gpt-5.6-sol` static-profile author session at extra-high reasoning; and
3. one independent `gpt-5.6-sol` static-profile review session at extra-high reasoning.

All use the pinned Codex CLI, Kevin's saved ChatGPT authentication, disposable state, no API keys,
no provider-billed calls, and no access to the deferred external-validation study.

## Bias and custody controls

The public fixture, author packet, semantic prompt, schemas, runner source, and hidden oracle are
digest-bound before execution. The oracle is stored separately and is loaded only after the three
construction roles finish. Neither model lane receives the oracle, expected source turns, routes,
or authoritative scope values. Raw traces are encrypted outside the repository; committed records
contain only typed outputs, digests, usage, and isolation receipts.

## Pass and stop rule

Both the compiled material and independently reviewed static material must be nonempty and match
the hidden active-state oracle exactly. Any missed durable behavior, false learning from an
ordinary request, wrong route, wrong scope, tool use, reroute, persisted session state, pin drift,
or packet drift fails the smoke.

A pass only makes the full v3 effectiveness grid eligible for a separate authorization. It does
not launch that grid and it does not change any v2.1 result. A genuine language-understanding miss
is preserved as a failed result; only defects in transport, schemas, isolation, or scoring may be
repaired and rerun under a new frozen version.

## Frozen instrument amendment 1.1

The first semantic-sensor role completed, then the initial profile-author launch was rejected by
the structured-output transport before it produced model output. The generated profile schema did
not mark every defaulted property as required. The original freeze and sensor result remain
unchanged. Amendment 1.1 closes that schema recursively and authorizes exactly one replacement
profile-author launch and the still-unused reviewer launch. It raises the total launch ceiling from
three to four while preserving a maximum of three successful role sessions. No prompt, evidence,
scope registry, oracle, sensor output, or expected answer changed.

The old wrapper raised before the orchestration layer could encrypt the failed trace; the sanitized
incident record therefore retains the failure and thread digests while explicitly recording that
capture limitation. This is an instrumentation defect and contributes no effectiveness evidence.
